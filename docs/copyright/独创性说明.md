# 独创性说明

> 本说明用于软件著作权申请，阐述本软件在技术上区别于同类产品的独创设计。
> 所有描述均可在源程序中对应查证。

## 一、软件定位

核核工具箱软件是一款 Windows 桌面一体化工具集合，集成 111 个独立工具。市面上虽有各类单一功能小工具，但本软件在**架构设计层面**解决了这些问题：

- 保活复用导致的异步任务失控
- 高危系统操作的判定边界难以精确
- 长时间任务的可靠中止

以下四项为本软件的核心独创技术点。

## 二、独创技术点

### 2.1 每次运行令牌（Per-Run Token）—— 异步任务生命周期的统一判据

#### 要解决的问题

桌面应用普遍采用页面保活（Keep-Alive）提升响应速度，但由此带来一类反复出现的缺陷：

1. **停止按钮在异步调用返回前无效**：用户点了停止，但启动请求尚未返回，此时没有可取消的对象
2. **切页后旧任务污染新界面**：用户离开页面又返回，上一轮任务的结果覆盖了新界面的状态
3. **多轮任务并发执行**：快速重复点击导致两轮任务同时写盘

传统做法是用布尔标记（如 `pageDead = false`、`isCancelled = false`），但布尔标记有致命缺陷：**新任务启动时把它重置为 false，旧任务看到的就是"未取消"**，无法区分"我这一轮"与"新一轮"。

#### 技术方案

本软件采用「每次运行领取自增序号」的机制：

```
启动任务：
  const runToken = ++taskRunSeq;    // 领取本轮的代次令牌

每个异步等待点返回后：
  if (runToken !== taskRunSeq) {
    // 本次运行已过期（用户点了停止，或已离开页面）
    killOwnJob();                   // 终止本次拿到的任务
    jobId = null;                   // 清空自己的引用
    unsubscribe();                  // 退订自己的事件
    return;                         // 不触碰界面
  }
```

关键点：**过期分支必须完成自己的清理**（终止任务、退订、清引用），但**不能触碰界面**——界面属于当前轮次。

#### 与现有做法的区别

| 维度 | 传统布尔标记 | 本软件的代次令牌 |
|---|---|---|
| 区分新旧轮次 | 不能 | 能（序号不同） |
| 停止在异步窗口内是否生效 | 无效 | 有效（序号已递增） |
| 旧任务收尾是否污染新界面 | 会 | 不会（token 判定后直接 return） |
| 并发任务是否可能同时写盘 | 可能 | 不可能 |

#### 实现位置

- 判据模块：`lib/run-token.js`（纯函数，可单测）
- 应用于 8 个长任务页面：文件内容搜索、Ping、路由追踪、下载、视频压制、视频裁剪、格式转换、环境安装

### 2.2 多路径电源操作门禁 —— 五类绕过方式的统一拦截

#### 要解决的问题

系统工具类软件通常提供"危险功能开关"，让用户自行决定是否允许关机、重启等高危操作。但传统的实现只识别**命令行的第一个词**：

```
判定逻辑：命令的可执行文件是否是 shutdown / Stop-Computer 等
```

这种判定可以被轻易绕过：

| 绕过方式 | 命令示例 | 传统判定 |
|---|---|---|
| 计划任务包装 | `schtasks /create /tr "shutdown /s"` | 首词是 schtasks，**放行** |
| at 命令定时 | `at 23:59 shutdown /s` | 首词是 at，**放行** |
| PowerShell CIM | `Invoke-CimMethod -MethodName Shutdown` | 首词是 Invoke-CimMethod，**放行** |
| WMI 方法调用 | `(Get-WmiObject ...).Win32Shutdown(2)` | 首词是 Get-WmiObject，**放行** |
| 计划任务 API | `New-ScheduledTaskAction -Execute shutdown` | 首词是 New-ScheduledTaskAction，**放行** |

结果是：用户以为"危险功能已关闭"，实际上软件内的命令执行工具仍能关机。

#### 技术方案

本软件的门禁判定分三层：

**第一层：整条命令行归一化后匹配**

不只看首词，而是把整条命令（含参数）归一化后，用正则匹配危险模式。例如 `schtasks /tr "shutdown /s"` 中的引号内容也会被识别。

**第二层：识别计划任务与 WMI 专用路径**

| 判据 | 覆盖的绕过方式 |
|---|---|
| `SCHEDULER_HEADS` | 计划任务的创建入口（schtasks 带 /create、at 命令等） |
| `WMI_METHOD_HEADS` | WMI/CIM 的关机方法调用 |
| `POWER_VERB_RE` | 电源动作动词（shutdown、restart、sleep、hibernate 等） |
| `.win32shutdown(` | WMI 对象的关机方法调用 |

**第三层：白名单豁免**

- `shutdown /a`（取消已安排的关机）**必须放行**，否则用户无法取消自己刚排的计划
- `schtasks /query`（查询计划任务）放行，这是只读操作
- `schtasks /end`（结束正在运行的计划任务）放行，不产生关机

#### 实现位置

`lib/power-gate.js`（纯函数模块，有独立的单元测试覆盖 14 条判定用例）

### 2.3 路径安全判定的边界精确化 —— 区分"自己的目录"与"他人的目录"

#### 要解决的问题

系统工具的删除操作为了防止误删系统文件，通常会维护一份"关键目录黑名单"（如 `C:\Windows`、`C:\Program Files`）。但这类黑名单存在两个对立的缺陷：

**缺陷一：漏拦** —— 用户主目录下的 `Documents`、`Desktop` 等文件夹如果被递归删除，损失可能比删系统文件夹更大（那里是用户数据）。

**缺陷二：误伤** —— 如果简单地把整个 `C:\Users` 加入黑名单，用户自己创建的 `C:\Users\我\Documents\我的项目` 也无法操作了。

#### 技术方案

本软件采用**边界判定**而非简单黑名单：

| 路径 | 判定 | 理由 |
|---|---|---|
| `C:\Windows`、`C:\Program Files` | 拒绝 | 系统关键目录 |
| `C:\Users`（Users 根本身） | 拒绝 | 会波及所有用户 |
| `C:\Users\我`（自己的家目录） | 拒绝 | 整个家目录不该被删 |
| `C:\Users\我\Documents` | 拒绝 | 一级子目录，数据集中 |
| `C:\Users\我\Documents\我的项目` | **放行** | 用户自己的具体工作目录 |
| `C:\Users\**他人**\Documents` 及更深 | 拒绝（`OTHER_HOME`） | 其他用户的数据 |

关键设计：

1. **家目录边界计算**：通过 `usersBoundary()` 确定 `C:\Users` 的位置，再判断目标路径是否落在"他人"区间
2. **盘符相对路径识别**：`D:`（不带反斜杠）在 Windows 上表示"D 盘当前目录"，会被解析成软件自己的工作目录，必须拒绝；`D:\` 才是盘符根
3. **设备保留名识别**：`CON`、`PRN`、`AUX`、`NUL`、`COM1` 等

#### 实现位置

`lib/path-guard.js`，导出 `checkDeletable` / `checkOverwritable` 等判定函数

### 2.4 零依赖的自动化测试体系 —— 217 个脚本 / 2404 条断言

#### 要解决的问题

Electron 应用的功能大量依赖**真实时序**（IPC 往返、页面切换、用户取消操作），传统的单元测试难以覆盖：

- Mock 掉 IPC 后，测的是 mock 的行为而不是真实实现
- 只做源码字符串匹配（"代码里有这行"）无法发现逻辑错误
- 引入 Jest/Vitest 会增加构建复杂度，且对 Electron 场景支持有限

#### 技术方案

本软件自研了一套零依赖测试框架（仅用 Node.js 内置能力）：

**（1）三层测试结构**

| 层级 | 数量 | 能力 |
|---|---|---|
| 纯函数单元测试 | 约 90 个脚本 | 直接调用 `lib/` 下的纯函数 |
| 行为测试 | 约 80 个脚本 | 从真实源文件中提取函数体，配 fake IPC/fake DOM 驱动真实时序 |
| 端到端测试 | 约 20 个脚本 | 启动真实 Electron，遍历 111 个工具页 |

**（2）行为测试的关键手法**

从源文件中按花括号配平提取**真实的函数体**，在受控环境中执行：

```
// 从 js/tools/sys-tools.js 提取真实的 cancel() 函数体
// 配上 fake invoke（可控制每次调用返回什么）
// 驱动「点击取消 → shutdown /a 返回 1116 → 断言状态」这一完整时序
```

这样测的是**真实实现**，而不是复制一份逻辑来测。

**（3）断言基线守卫**

维护 `assertions-baseline.json` 记录每个测试脚本的断言条数。任何脚本的断言数**低于基线即报错**，防止"悄悄删用例让测试变绿"。

**（4）变异测试验证**

关键测试用「故意注入 bug」验证其有效性：把修复改回缺陷状态，确认测试会失败。例如把 `onceId` 过滤改回"撤销全部"，对应的两条断言立刻失败并给出精确报错。

#### 实现位置

- 测试框架：`scripts/lib/harness.js`、`scripts/run-tests.js`
- 测试用例：`scripts/test-*.js`（217 个）
- 断言基线：`scripts/assertions-baseline.json`
