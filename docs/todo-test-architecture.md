# 待办：测试架构的进一步模块化（方案 C）

> 状态：**未开始**，等有完整的工作轮次再做。
> 本文档记录方案、动因与风险，避免"想做但忘了当初为什么"。

## 当初为什么没立刻做

2026-11 做了一轮"测试太慢"的优化，比较了三个方案：

| 方案 | 做法 | 改动量 | 风险 |
|---|---|---|---|
| **A：功能域映射**（已做） | 维护一张「功能域 → 源文件/测试」表，按改动反查该跑哪些 | 小 | 低 |
| B：目录化 | 把测试按功能域分目录 | 中 | 中 |
| **C：契约层**（本文档） | 抽出功能契约，守卫测试改为遍历契约 | 大 | 高 |

**已做 A**，效果：全量 310s → 单域 1-15s，改 `pdf-plus.js` 只跑 1 个测试。
B 没做（搬家风险大、收益只是"人看得清楚"）。C 记在这里。

## C 要解决的问题

A 解决了"跑哪些"，但没解决**"全局测试太脆"**：

现在有 41 个测试属于 `core` 域，其中相当一部分是"全项目一致性检查"——
它们硬编码遍历**所有** 106 个工具 / 所有通道 / 所有源文件。结果是：

- 加一个新工具，可能同时让 5 个全局测试变红；
- 工程师看到红就改测试的期望值，而不是想"这里是不是该用契约";
- 全局测试的"通过"渐渐变成"我们把它改绿了"，而不是"系统真的没问题"。

## C 的做法（三步）

### C1. 抽出功能契约

新建 `lib/contracts/`，每个功能域一个 `xxx.contract.js`：

```js
// lib/contracts/pdf.contract.js
module.exports = {
  name: 'pdf',
  channels: ['pdf:merge', 'pdf:split', 'pdf:watermark'],  // 它拥有哪些通道
  tools: ['pdf-tools', 'pdf-watermark', 'pdf-slim'],       // 它注册哪些工具
  deps: ['pdf-lib'],                                       // 它依赖什么
};
```

### C2. 守卫测试改为契约驱动

现在的写法（硬编码遍历全部）：

```js
// 伪代码
for (const tool of Registry.all) {
  assert(ORDER[tool.module].includes(tool.id), tool.id + ' 未登记进 ORDER');
}
```

改成：

```js
for (const contract of allContracts()) {
  for (const toolId of contract.tools) {
    assert(ORDER[contract.name].includes(toolId), ...);
  }
}
```

效果：加新工具只需更新**它所属的契约**，其它域的守卫完全不受影响。

### C3. 功能包自治（可选，最后做）

```
features/
  pdf/
    index.js       # 工具注册
    contract.js    # 对外契约
    test.js        # 只测这个功能
```

这一步把源文件也按域切开，改动最大。

## 风险与前置条件

- **高**：要动 106 个工具的注册方式、`main.js` 的通道注册、以及全部
  41 个 core 域测试。中间任何一步出错都是大面积红。
- **前置**：等项目处于相对稳定的阶段（没有并行的大功能开发），
  且愿意接受"这一轮不产出功能、只产出架构"。
- **建议顺序**：先做 C1+C2（只改测试侧，不动源码），
  观察一段时间再决定要不要做 C3。

## 折中方案（如果没时间做完整 C）

只把**最容易漂移的那几条**改成契约驱动，其余保持现状：

1. 「所有工具都在 ORDER 表里」→ 改为遍历契约的 tools
2. 「每个工具都有英文标题」→ 同上
3. 「index.html 引入的脚本都在包里」→ 改为遍历契约声明的入口

这三条是"加新工具时最容易红、也最容易被改绿"的，改完收益最明显。

## 触发条件

出现下列任一情况时，就该把这件事提上来：

- 加一个工具需要改 3 个以上测试的期望值；
- 全局测试红了之后的第一反应是"改成新数字"而不是"查原因"；
- 同时有两人以上在加功能（契约的收益随人数上升）。
