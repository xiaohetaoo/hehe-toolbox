# 剥注释必须先识别正则字面量

## 现象

朴素地扫描「`//` 到行尾」与「`/*` 到 `*/`」会把正则字面量内部的字符
当成注释起点或字符串起点，此后整个扫描状态错位。

具体触发点：`js/tools/net-tools.js` 里有一句

```js
raw.replace(/[\x00-\x1f<>:"|?*]/g, '_')
```

正则内部的这个**双引号**如果不被识别为正则的一部分，就会被当成
字符串开头，一路吞到 2907 个字符之后的另一个双引号上。之后所有
注释/字符串判断全部错位：明明存在的块注释剥不掉，
依赖它的断言变成**假绿**（不报错，只是因为恰好没有触发点）。

## 实测方法

- 用一个只做「引号配对」的朴素剥离器处理 `js/tools/net-tools.js`，
  然后断言「块注释必须被剥掉」—— 实测失败，且失败位置在第 2900 字符之后。
- 换成会识别正则字面量的实现后，同一断言通过。
- 反向验证：把 `regexAllowed` 的判据改错（把除号当正则），
  会有一批正常代码被当成正则吞掉，断言同样变红。

## 结论

- 判断「`/` 是除号还是正则开头」的通用启发式：看 `/` 之前最近的**有效 token**。
  值是标识符/数字/字符串/右括号/右方括号 → 除号；其余（`( , = : [ ! & | ? { } ;`
  以及 `return`/`typeof`/`case` 等关键字）→ 正则。这是 JS 词法分析的标准做法。
- 项目里**只能有一份** `stripComments`。历史上三个测试脚本各自实现/各自抽取一份，
  一个地方修了正则识别，另一个地方的旧实现还在用朴素扫描，行为不一致。
- 正则不能跨行：遇到 `\n` 就认为「刚才判错了」，放弃当前正则，
  按除号处理 —— 这条兜底避免了错误扩散。

## 影响到的代码位置

- `lib/src-scan.js:27` `regexAllowed()` —— 判据本体。
- `lib/src-scan.js:47` `stripComments()` —— 唯一实现。
- `lib/src-scan.js:100` `scanBrace()` —— 同样要跳过正则，否则 `{` `}` 会数错。
- `scripts/lib/harness.js:59` `readSrc()` —— 所有源码断言的入口，默认走这套剥离。
- `scripts/test-i18n-coverage.js` —— 用**真实文件**做输入的行为断言
  （编造的简化样例不一定能复现这种状态错位）。
