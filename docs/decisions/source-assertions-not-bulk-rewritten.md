# 为什么「420 条源码断言要改写成行为断言」这件事没有做

> 记录于 v0.4.1（D3 项被评估后放弃）
> 结论：**这个目标在当前判据下不可操作，强行做会让测试变得更差**

## 起因

交接文档里有一条遗留：项目 716 条源码匹配断言中，有 420 条没写「锁的是」
（说明它在锁哪个回归）。按 harness 的规矩（`scripts/lib/harness.js` 第 34 行），
每条源码断言都该说清「锁的是哪个历史回归 + 为什么不能用行为断言替代」。

于是很自然的想法是：把这 420 条逐步改写成行为断言。

## 尝试与失败

### 第一次尝试：按「脆弱度」筛选

设想是找那些"只匹配字面形式、改实现就假红"的断言，优先改掉。

写了脚本扫描，按三种模式归类：顺序断言（`indexOf(A) < indexOf(B)`）、
变量名耦合（`const x = require(...)`）、空白敏感（正则里含 `\n` 或连续空格）。

结果：命中 27 条，抽查后发现**大部分是误判**。
例如 `const fn = mainSrc.match(/async function foo\(\)[\s\S]*?\n\}/)` ——
这确实含 `\n`，但它是"从源码里切出函数体，再对函数体做行为检查"的**辅助步骤**，
不是断言本身。把它算成脆弱断言没有意义。

### 第二次尝试：找「空匹配仍 PASS」的静默失效

这一类确实危险：如果断言写成

```js
const items = [...src.matchAll(/某正则/g)];
assert.deepStrictEqual(items.filter(坏), []);   // 空数组恒成立
```

那么正则一旦不匹配，这条断言就**永远绿**，而它保护的东西已经没人检查。
本轮真踩过：`test-job-stream-isolation` 靠正则数 job 前缀，拆分后写法变了、
正则匹配不到——那次因为还要求"至少 10 个"所以红了，但门槛若写成 9 就会永久失效。

写扫描器后命中 30+ 处，但抽查发现**绝大多数是误判**：

```js
for (const m of src.matchAll(/handle\('([^']+)'/g)) set.add(m[1]);
```

这是"收集所有匹配项到集合"，后面通常还有对集合内容的断言，不是空集合恒真。
我的扫描器把「for-of 遍历 matchAll 结果」一律当成危险形态，太粗。

连自检都写不顺：想造一个"正例 + 反例"来验证扫描器，结果发现
正则形态太多样，判据写出来要么漏要么误伤。

## 结论：判据不成立

两次尝试都卡在同一处：**「源码断言」不是一个同质的类别**。它至少包含四类：

| 类型 | 例子 | 该不该改 |
|---|---|---|
| 结构性事实 | "门禁只在 main.js 的包装层里"、"index.html 引入了 lib/exif.js" | **不该改**。没有行为可以验证——这两种文件本身不执行 |
| 切片段再检查 | `const fn = src.match(/async function foo.../); assert(fn.includes('x'))` | 可改，但成本高（要造能触发该分支的真实输入） |
| 收集统计数据 | "有 168 个通道"、"工具数 ≥90" | 部分可改（跑一次数一遍），但慢几十倍 |
| 真正的防御性检查 | "uncaughtException 必须调用 recordCrash" | 不该改。验证它需要制造真实未捕获异常，那会杀死测试进程本身 |

第一类和第四类**本质上只能静态检查**。而它们在 420 条里占了相当比例。
盲目"改写成行为断言"的结果不是提高质量，是：
- 把「文件里有没有这行配置」改成「起一个 Electron 验证」——慢 100 倍，一样不精确
- 或者干脆删掉——**测试覆盖率净下降**

## 实际做了什么（替代方案）

放弃了"全量改写"，改为守住增量 + 补真正缺的判据：

1. **增量已守住**：SA-4 元检查要求**新写的**源码断言必须写「锁的是」。
   这条一直在生效——本轮 5 个提交新增的源码断言全部带了说明，
   期间红过 3 次都是它拦下的。
2. **补了「静默失效」的真实案例**：`test-job-stream-isolation` 的正则
   从认 2 种写法扩到认 4 种，并在注释里写明"少认一种的后果是静默漏统计"。
3. **补了「守卫本身失效」的教训**：`check-assertion-count.js` 在遇到
   `run-tests.js` 收集器时展开不到脚本，等于整个断言数守卫失效；
   且第一次修的时候按全量清单展开，导致总数虚涨到 2784（看着更安全，
   实际分母虚高、少跑一整个分组都发现不了）。这两点都写进了 D4 的提交说明。

## 给后来者

如果要做这件事，**先建立可操作的判据**，再动手：

- 不要按「有没有写注释」筛，那只是文档完备度，不是质量
- 不要按「是不是正则」筛，正则本身不是问题，**匹配结果有没有被校验**才是
- 可行的起点：找出「断言里出现 `.filter(` + `deepStrictEqual(..., [])`
  且同一函数内没有 `.length` 检查」的，逐个看过再改。
  本轮试过这个判据，能命中真问题，但需要人工逐条判断，
  不适合批量脚本化
