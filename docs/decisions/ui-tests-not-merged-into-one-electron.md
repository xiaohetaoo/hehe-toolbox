# 为什么 UI 测试不合并成「一次 Electron 启动」

> 记录于 v0.4.1（D1 项被评估后放弃）
> 结论：**省 40 秒不值得把 21 个独立测试捆成一个**

## 现状

`npm run test:ui` 跑 21 个脚本，每个脚本自己：

```js
const runner = [...拼一个 Electron 脚本...].join('\n');
execFileSync(ELECTRON_EXE, [runnerFile], { env });
```

实测耗时分布（v0.4.1）：

```
UI 段总计            122.4s
其中 Electron 冷启动   约 40s（21 次 × 实测 1.9s）
测试逻辑本身           约 82s
```

## 合并能省多少

实测「启动 + 加载 index.html」= **1900ms**（单次冷启动的纯开销）。

理论最优：21 次 → 1 次，省下 20 × 1.9s ≈ **38 秒**，UI 段从 122s 降到 84s。

全量 `npm test` 当前约 155 秒，会降到约 117 秒。

## 为什么不这么做

### 1) 失去故障隔离，这一条最要紧

现在任何一个 UI 测试崩溃，你能立刻知道是哪个：

```
[14/110] test-danger-inline-enable.js  FAIL  6.1s
```

合并后 21 个探针跑在同一个 Electron 进程里，某个探针把进程搞崩
（比如 `test-snip-e2e.js` 真的去截屏、`test-two-pass-e2e.js` 真跑 ffmpeg），
**后面所有测试都不再执行**，而报告只会说"第 N 个探针失败"。

这类"一个挂全挂"在 CI 上表现为莫名其妙的全红，排查成本远高于省的 38 秒。

### 2) 状态污染需要逐个处理，工作量不小

抽查发现至少 6 个测试依赖**自己的初始状态**：

| 测试 | 依赖 |
|---|---|
| `test-i18n.js` / `test-tray-i18n.js` | 语言必须是初始态（否则断言的前提不成立） |
| `test-danger-inline-enable.js` | 高危功能必须是关闭态 |
| `test-home-search.js` | recents 必须为空 |
| `test-improvements-a.js` | 参数记忆必须无历史（否则回填值已被污染） |
| `test-keyboard-a11y.js` | 同上 |

合并后每个测试都要显式"重置到干净状态"，而重置本身要么重载页面（又要 1.2s，
省下的时间吐回去），要么写一套清理逻辑（21 份，容易漏）。

### 3) 收益随测试数增长，但当前规模不值得

省的是「测试数 × 1.9s」。当前 21 个 → 38 秒。
如果将来涨到 60 个，省 112 秒，那时候才值得做。

**现在做的性价比是负的**：改动 21 个文件（每个都要适配共享进程的生命周期），
换来开发时每次 `npm test` 少等 38 秒。

## 如果将来要做

按收益排序的三步走，不要一次全合并：

1. **先合并最慢的几个**（`test-file-unlock-e2e.js` 12.2s、
   `test-acl-gate-e2e.js` 9.8s、`test-acl-diagnose-e2e.js` 9.7s ——
   这三个共 31.7s，合并后约 22s，省 10s）。
   它们都是 ACL 相关、共享同类 IPC 桩，状态耦合小。
2. 把「共享一个 Electron 实例」做成 `scripts/lib/e2e-session.js`，
   提供 `openWindow()` / `resetState()` / `closeAll()`，
   而不是让每个测试自己拼 runner 脚本。
3. 确认稳定运行一段时间（至少 20 次 CI 无 flaky）后，再逐步并入其余测试。

## 顺带说明：D4 已经解决了真正的痛点

D1 的动机之一是"测试跑得慢"，但本轮实测后发现问题不在总时长，
而在**加测试的成本**：原来的 `test:unit` 是一行 3955 字符的 `&&` 链，
加一个测试要改那一行，而且漏登记就等于没跑（已经发生过两次）。

D4 把这些解决了：`scripts/run-tests.js` 自动发现、自动分组，
`package.json` 里只剩 62 字符。这才是日常真正会碰到的东西。

至于总时长，155 秒里 82 秒是测试逻辑本身（真跑 ffmpeg、真截屏、真改注册表），
那部分**不该也不该省**。
