## 修掉一个真实的安全缺陷：电源门禁可被绕过

「系统电源操作」是高危功能，默认关闭，只有用户显式开启后 `shutdown` / `Restart-Computer` 这类命令才会被放行。审查发现**有 8 种写法能绕过它**：

| 绕过写法 | 为什么会漏 |
|---|---|
| `start /b shutdown /s` | `start` 的第一个参数可以是它自己的开关，剥壳后首词成了 `/b` |
| `start /min shutdown /s` | 同上 |
| `start /wait shutdown /s` | 同上 |
| `start "" /b shutdown /s` | 同上（标题为空串 + 开关） |
| `start /b cmd /c shutdown /s` | 剥完 `start` 后首词是 `cmd`，里层的 `shutdown` 从没被看到 |
| `start cmd /c shutdown /s` | 同上 |
| `Start-Process shutdown` | PowerShell 版的 `start`，语义等价，但完全没被处理 |
| `powershell -c "Start-Process shutdown"` | 同上 |

有个细节能说明问题出在哪：`start shutdown /s`（后面直接跟程序名）**原本就拦得住**，只有中间隔了开关才漏——说明漏的不是「start 没被处理」，而是「开关没被剥」。

修复只改「怎么取首词」这一个函数，没有改动任何危险词表或放行规则。

**两侧都验过**：
- 15 条危险变体现在全部拦住
- 28 条日常命令（`del shutdown.log`、`tasklist | findstr shutdown`、`start notepad`、`Start-Process notepad`、`ffmpeg`、`npm test`…）**零误拦**

这一点很重要——这个门禁的失败有两种：漏拦会让用户在没开开关的情况下关机/重启，误拦会让正常命令用不了。只测一边不算修好。

## 4 项「测试假绿」

这些断言看着在跑，实际上什么都没测到。修复后每一项都做了**反向验证**（故意制造回归，确认测试真的会变红）：

1. **降级测试污染全局**。它把 `globalThis.TextDecoder` 改成只认 utf-8 且不还原，导致同文件后续 12 条用例都在错误环境里跑——而当时全绿，因为后面的断言恰好不依赖 GBK 解码器。改为子进程隔离，并加一条「本进程未被污染」的回归锁。

2. **0 条用例也能全绿**。探针失败时 0 条断言被注册，harness 打印「0 通过 / 0 失败」并 exit 0，CI 的 `grep` 抓不到任何东西——4 条断言就此凭空消失。改在 harness 出口处统一拦：一条用例都没注册直接判失败。这样所有脚本自动受保护。

3. **审计测试被自己喂饱**。通道审计扫「渲染层有没有调用某个通道」，却把常量表 `js/channels.js` 本身也扫了进去——表里有哪个通道，就等于「渲染层调用了哪个通道」。实测删掉一个真实调用点，断言照样通过。修复后又发现第二层：迁移到常量后的通道是用 `Channels.CHANNELS.X.Y` 引用的，只扫字面量同样看不见，两处一起修才对。反向验证：改坏一个调用点，两条断言同时变红。

4. **测试测的是测试自己**。某条断言定义了执行真实源码的函数却**从未调用**，真正跑的是另写的一份同构副本。实测把源码里 `sw = sel.w * dpr` 改成 `sw = sel.w`（高分屏下截图会横向错位），6 个断言仍然全绿。改为真正执行源码片段。

## 其余修复

**12 项断言目标错位**——改坏了也不会红。例如：
- 一条「解码下限」断言写成恒真式（只要源码出现过某个标识符就为真），把下限从 56 改成 72 照样绿 → 改成行为断言：56 字节必须解得开、55 字节必须报错
- 一条「handler 保护」用 `'\n});'` 定位结尾，但搬到 `ipc/` 后的收尾是 `'\n})'` → `indexOf` 返回 -1，切片直接跑到文件末尾。实测某个 handler 抽出了 14732 个字符（真实长度几百），断言实际在扫整个文件
- 一条断言先把目标串替换成它自己再匹配，结构上不可能失败
- 一条测试在 `onClose` 没接 `resolve` 时会**永久挂住**（CI 表现为超时杀进程，看不到任何失败信息）→ 加 `Promise.race` 超时，2 秒内报清晰 FAIL

**6 份重复的注释剥离实现**统一到 `lib/src-scan.js`。实测同一份 `main.js`：朴素实现剥后 164145 字符，统一实现剥后 163767 字符——差的 378 个字符是遗漏的行尾注释，它们会参与后续正则匹配。

**9 处「用注释当代码边界」**改成括号配平。注释一改写，这些测试就会误报「找不到 xxx」，而实现完全正常。

**2 处静默跳过**改成显式 `SKIP` 前缀（CI 会作为 annotation 报出来，人能看见「这一轮少测了」）。

**1 个真实 NUL 字节**（注释里写正则字面量时留下的）导致 git 把整个测试文件当二进制、`grep` 判为 binary。

## 发布流程加固

v0.3.7 的 Release 正文是空的，而 v0.3.6/0.3.5/0.2.8 都有。排查确认：`release.yml` 在两次之间**完全没改**、权限够、步骤都成功——是 `action-gh-release` 的 `generate_release_notes` 行为不稳定（上游有同类 issue）。

结论是不把「有正文」寄托在第三方 action 的一个布尔参数上。新增 `scripts/ensure-release-notes.js`：发布后检查正文，为空就用 GitHub 的 generate-notes API 补上；已有正文时幂等退出。这一步刻意**不挂红**——资产已上传能下载，正文缺失是「说明不完整」而非「发布失败」。
