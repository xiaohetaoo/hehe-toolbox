# v0.4.4 —— 修一个「功能整体失效、但从不报错」的缺陷

这一轮全部来自一份代码审查报告：1 个 P2 实证缺陷 + 8 个 P4 待清理项。
P4 那批按原话是「均已留证据，按需清理」，我把它们一并做了 ——
其中三条属于「代码在跑、但跑的不是注释说的那件事」，这类问题不修会一直误导后来者。

**没有用户可见的行为改动**，除了下面第一条（它是修复）和最后一条（视觉）。

## EXIF 批量重命名：这条路径从来没有读过 EXIF

「按拍摄时间批量重命名」是个明确宣传的功能，实际从上线起就没生效过。
两层缺陷叠在一起，而且**两层都自己不会报错**：

1. `fs:read-file-b64` 返回的是 `{ b64, size }` 对象，渲染层却当 base64 字符串
   直接 `atob()` → 每次都抛 `InvalidCharacterError` → 被 `catch` 吞成 `t = null`
   → 退回文件修改时间。
2. 传的第二个参数 `65536`（注释宣称「只读文件头 64KB」）主进程根本不收 ——
   签名只有 `(e, p)`，第三参被 IPC 静默丢弃。**那个优化从未存在。**

结果：每一张照片都被改成**下载/复制那一刻**的时间，而界面写着「按 EXIF 拍摄时间命名」。
用户拿到的日期全是错的，且没有任何提示。

修法：渲染层按 `r.b64` 取值；handler 真的支持 `maxBytes`（`open` + `read` 前 N 字节，
不用 `readFile` + `subarray` —— 那样仍然整份读进内存，省不了 IO 也省不了内存）。
非法值一律当「没传」退回整读：静默读成 0 字节比多读 5MB 危险得多。

### 这类缺陷为什么之前没被发现

全项目 19 处同类调用都是 `r.b64`，唯独这一处错。
而这条路径的每一个错误都被 `catch` 吃掉 —— **静态断言能证明「代码里有 r.b64」，
证明不了「路径真的跑通了」**。

所以新增 `scripts/test-exif-rename-e2e.js`：把 `ipc/fs-ops.js` 的 handler 表
在纯 Node 下加载起来（`scripts/lib/load-fs-ops-handlers.js`），喂真实字节布局的
JPEG，断言最终算出的文件名是 `2024-11-03_143022` 而不是 mtime 的 `2030-01-01_080000`。
两个变异测试都验证过：改回任一层的原写法，这条立刻红。

### 两个「测试自己也会犯同样错误」的插曲

修 `\d` 那条时，我在测试里写的 `\d` 同样被模板字符串吃掉，
导致新加的 ETA 断言**恒真**（正则永远匹配不到，秒数恒为 0）。
直到做变异测试（把修复删掉、看断言会不会红）才发现。

同样的事发生在参数记忆那条：第一版选 `diff3` 页测试，那页只有 textarea，
`store` 一直是 `null` —— 「没记住正文」和「整页都没记」表现一样，断言空转。
第二版选 `csv-json`，它的 textarea placeholder 含「粘贴」，本来就被另一条规则排除 ——
把标签名过滤删掉后断言照样绿。最终换成翻译工具的页面（placeholder 是
「输入要翻译的文本…」，不命中任何过滤词），才真正测到东西。

**这两次都不是「写错代码」，而是「写了一断言不会真的失败」的测试。**

## 新增的两道守卫

- **跨进程事件对账**（`test-ipc-channels.js`）：主进程 `send()` 的每个事件名，
  渲染层必须有订阅。推送和订阅分居两个进程，任一边失效运行时都**完全静默**。
- **图标一致性**（`test-icon-consistency.js`）：界面源码里的彩色 emoji 行数
  不许超过基线（35 行，只能往下走）。判据刻意排除 `✓ ✗ ★` —— 它们是普通文字
  符号、跟随 `currentColor`，与那批 `⚠ 🚀 ✅` 不同。
