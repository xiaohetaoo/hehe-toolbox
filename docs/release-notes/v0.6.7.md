# v0.6.7 —— 命令收藏能收藏了；堵住 PowerShell 编码参数的缩写绕过

这一版修了三件事：一个**真机上 100% 复现的功能断链**，一个**电源门禁的安全绕过**，
一个**会让录音页永远转圈**的挂死。另外做了一次覆盖 103 个工具的过夜深度审查。

## 一、P0：命令收藏 / 快捷启动栏的「添加」100% 失效

**现象**：「收藏命令」点进去，三步弹窗（名称 → 命令内容 → 选择 CMD/PowerShell）
全部正常走完，然后**什么都没发生**——没有提示，列表不刷新，重启后也没有。
快捷启动栏的「添加」同样。

**根因**在 `js/tools/launch.js` 的 `pickOne()`：

```js
btn(label, 'btn-secondary', () => { md.close(); resolve(val); });
```

`md.close()` 会**同步**触发弹窗的 `onClose: () => resolve(null)`。
Promise 只认第一次 resolve，所以 `null` 先被锁定，后面的 `resolve(val)` 是无效调用。
`pickOne` 永远返回 `null`，调用方的 `if (!shell) return` 直接静默退出。

修复只有一行——调换顺序：

```js
btn(label, 'btn-secondary', () => { resolve(val); md.close(); });
```

**真机全链路验证**：添加「夜审修复验证 / echo fixed-verify / CMD」→ 列表出现 →
写入 `%APPDATA%/核核工具箱/hehe-data.json` → 点执行输出 `fixed-verify`、退出码 0 →
删除后 `commands` 回到 `[]`。

同类问题全项目复查：`ui.js` 的 `confirmBox` / `promptBox` 本就规避了这个陷阱
（前者用 `done` 标志、后者先赋值再关闭），只有 `pickOne` 裸用 `modal` 才踩到。
新增 `scripts/test-pickone.js` 把这个顺序钉死。

## 二、安全：`-EncodedCommand` 的缩写形态绕过了电源门禁

电源门禁的作用是「这条命令会不会关机/重启」，命中就拦。旧实现只认两个字面量：

```js
/-EncodedCommand|-e|-[a-z]*e/
```

但 PowerShell 的参数允许**无歧义前缀缩写**。实测（直接 spawn `powershell.exe`，
载荷 `Write-Output PWNED`，换第二段载荷 `ZZZ-DISTINCT` 复验）：

| 写法 | 实际行为 |
|---|---|
| `-e` | **会执行 base64 载荷** |
| `-ec` | **会执行**（注意它不是 `encodedcommand` 的前缀） |
| `-en` `-enc` `-enco` `-encoded` … | **会执行**（真前缀，长度 ≥2 全部有效） |
| `-ea` `-ep` `-ex` | 不执行（被当成别的参数） |
| `-eb` `-ed` … `-ez` `-ecc` `-ence` | 不执行（报 not recognized） |
| `-ExecutionPolicy` `-File` `-NoExit` | 不执行（正常参数） |

旧正则的 `-[a-z]*e` 只覆盖「以 e 结尾」，中间的 `-ec` / `-enc` / `-enco` **全部放行**。

改为两条判据的并集：

1. 开关名是 `e` 或 `ec`；
2. 开关名是 `encodedcommand` 的前缀且长度 ≥2。

单字符 `-e` 在别的命令行里是常见开关（`findstr -e`），所以它仍然只在命令行确实是
`powershell` / `pwsh` 系时才生效，与旧实现的保守程度一致；`-ec` 与其他前缀没有
第二含义，不必限定外壳。`/ec` 是 cmd 那侧的旧写法，判据不变。

`scripts/test-powergate.js` 新增 **PG-ENC-1 ~ 7（7 条断言）**，把上面这张表逐行钉住——
「会执行的一个不放过」和「不执行的一个不误伤」两侧都有断言。

## 三、录音页假死：dshow 设备枚举没有超时

`listDshowDevices()` 原来只靠 `exit` / `error` 两个事件收尾。只要 ffmpeg 既不退出
也不报错，这个 Promise 就**永不 resolve**——而它的调用方正是录音页打开时拉下拉框的
`rec:audio-devices`。表现：下拉框永远转圈，切走再切回来还是转圈，主进程没崩、
日志没有报错，只是那条通道再也不回话。

实测过的卡死形态（都不产生 exit 也不产生 error）：摄像头驱动被别的会议软件占着、
虚拟摄像头卸载后注册表残留、蓝牙音频设备休眠时 `OpenDevice` 阻塞在驱动里。

加 15 秒超时兜底，并且**超时后必须 kill**：只 resolve 不杀的话，那个 ffmpeg 会一直挂着，
用户来回切几次就是一堆孤儿进程，且它们可能正占着摄像头，让新一次枚举也失败——
从「偶尔卡住」恶化成「永远拿不到设备」。

几点刻意的选择：

- **15 秒不是 3 秒**：实测设备多的机器枚举要 2~5 秒（每个设备都要 Open/Close 一次
  拿能力信息）。取值太紧会把「慢」误判成「挂」，用户设备列表变成空的——那是把一个
  偶发卡死换成每次必现的空列表，更糟。
- **超时返回空列表而不是抛错**：录音页对空列表已有「无可用设备」的展示分支，
  抛错会让整页报红。
- **`timer` 必须先声明成 `let timer;`**：`settle` 里要 `clearTimeout(timer)`，
  而 `settle` 可能被 `error` 事件更早调用。写成下面的 `const timer` 会命中 TDZ，
  把「枚举失败」升级成「主进程抛异常」。
- **`timer.unref()`**：它只是兜底，不该拖住进程退出。

新增 `scripts/test-dshow-timeout.js`（**D1 ~ D7，7 条断言**），用真函数跑三种路径：
挂住时必须 resolve、超时后必须 kill、正常退出时必须**不** kill。

## 四、顺手统一的 ffmpeg 进程收尾

`ipc/media-ffmpeg.js` 里原本有 5 处几乎一样的内联「杀 ffmpeg」代码，复制粘贴时
漏掉 `taskkill` 那行就会留下编码子进程，表现是「点了取消，CPU 还满载」。
抽成 `killFfmpegTree(proc)` 统一处理（先 `proc.kill()` 同步发信号，再
`taskkill /pid … /t /f` 兜子进程；顺序反过来会让紧接着读进程状态的调用方看到旧状态）。

## 七、过夜深度审查（无代码改动的部分）

除了上面这些，还做了一轮覆盖全部 103 个工具的静态审查 + 真机走查，结论是以下几块
**确认无恙**，记录在此以免下次重复投入：

- **渲染层注入面**：208 处 `innerHTML`，21 处带插值，全部经 `escapeHtml` 或为数字型；
  无 `eval` / `new Function` / `document.write` / `insertAdjacentHTML` / `outerHTML`。
- **资源泄漏**：7 处 `setInterval` 全部有清理路径；21 处 `api.on` 订阅全部有
  unsub 或 `onCleanup` 兜底。
- **IPC 校验**：通道表 174 条 ↔ `handle()` 引用 174 条 ↔ 主进程 110 处注册，一一对应；
  `EXEC.RUN/STREAM` 的电源门禁按整条命令判定；`JOB.KILL` 归属校验完备。
- **安全边界**：CSP 无 `unsafe-eval`；`contextIsolation` 开启；`isDev` 由主进程注入。
- **生命周期**：`before-quit` / `will-quit`（flushStore + clearMarker + unregisterAll）/
  `window-all-closed` / `second-instance` 单例还原链完整。

**一处环境问题的定性**（不是代码问题）：本机「文件占用解锁」查询会稳定返回
「Restart Manager 查询失败（错误码 5）」。用探针截获应用内真实的 `execFile` 调用后确认：
同一构造、同一无锁状态，系统 node 与 `ELECTRON_RUN_AS_NODE` 都成功，只有 Electron
**GUI 主进程** spawn 的 PowerShell 失败——本机 360 安全卫士拦截了它调用 Restart Manager。
CI 与无 360 的机器不受影响。详见 `docs/decisions/restart-manager-rejects-directories.md`。
