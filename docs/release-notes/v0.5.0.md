# v0.5.0 —— 新增「视频裁剪」

一个工具，只做一件事：从一段视频里按时间截出一个片段。

## 为什么是「最简单的裁剪」

不做转场、不做多段拼接、不做滤镜、不做时间线拖拽 —— 那些是剪辑软件的活。
一个「什么都能做」的页面，第一次打开时用户得花几分钟找「我该点哪儿」；
而这个工具的场景极其明确：录屏太长要截中间一段、视频前 30 秒是片头不要了。

## 真正花时间的地方：怎么让用户**决定**切在哪

裁剪的难点从来不是执行，而是选切点。只给两个数字输入框的话，
用户得先用别的播放器看到 3:42，再回来手打 3:42 ——
而人眼估时间普遍差半秒到两秒，打错一个数字就得整段重来（重编码动辄几十秒）。

所以这个页面带了**预览播放器**：拖到合适的位置，点「设为起点」/「设为终点」，
起止时间自动回填。也可以直接输入 `mm:ss.mmm` 或纯秒数（`42` 也认）。

播放 `<video>` 能不能加载本地文件，在 Electron + 本项目 CSP
（`media-src 'self' blob: file:`）下**是实测过的**，不是假设：
`file:///` 视频能加载元数据、能 seek。实测记录见交接文档。

## 两种模式，代价写在界面上

| | 精确模式（默认） | 快速模式 |
|---|---|---|
| 原理 | 重新编码 | `-c copy` 流复制 |
| 速度 | 与片段长度成正比 | 几秒 |
| 起点 | **精确到帧** | **吸附到最近关键帧** |
| 画质 | 有极小损失 | 无损 |

这不是"两种都好"，而是明确的取舍。实测数据（10 秒源、关键帧间隔 2 秒、
请求从 3.0s 切 2 秒）：

| 模式 | 实际时长 | 首帧与源 3.0s 帧的 PSNR |
|---|---|---|
| 精确 | 2.000 秒 | 39.97 dB（几乎一致） |
| 快速 | 3.080 秒 | 12.19 dB（完全不同，实际从 2.0s 开始） |

也就是说快速模式下用户要求的 3.0s 根本没生效，实际从 **2.0s** 开始，
还多出 1.08 秒。这是流复制的固有限制，不是参数没调对 —— ffmpeg 会把
`-ss` 之前的关键帧也带上，再用 `-avoid_negative_ts` 把时间轴归零。

所以界面上明写了这条代价，而且**成品完成后显示的是实际时长**：
如果与请求差了 0.15 秒以上，会标黄并说明"快速模式会把起点吸附到最近的关键帧"。
用户看着「2.00 秒」却拿到 3.08 秒的文件，下次就不敢信这个工具了。

## 实现要点

- **`-ss` 放输入侧**。实测输入侧与输出侧在重编码时精度相同（ffmpeg 2.1 之后
  输入侧会解码后丢弃到目标点），但输入侧对长视频更快。这里不牺牲精度换速度。
- **`-stats_period 0.2` 必须设**。ffmpeg 默认每 0.5 秒才发一次进度块，
  而裁 4 秒片段只要 0.6 秒 —— 整个过程只发得出 **1 条**进度，
  界面从 0 直接跳到 99%，等于没有进度条。实测三种周期：
  默认 2 条 / 0.1 秒 6 条 / 0.05 秒 9 条，取 0.2 兼顾流畅与 IPC 开销。
- **失败和取消都必须删半成品**。ffmpeg 被 SIGKILL 时会留下几十字节的残片，
  留着的话用户会以为"切成功了，只是短了点"，而那个文件可能在中间就断了。
- **输出走 `fs:unique-path`**。这类工具的典型用法是反复调参数试切，
  固定输出名会让每次试切覆盖上一次，用户没法比较。

## 一个被单测抓出来的输入校验缺口

`Number(null) === 0`、`Number('') === 0` —— 所以只写 `Number(start)` 的话，
缺参数的调用会被静默当成「从 0 秒开始」。对 `start` 而言 0 是合法值，
于是这个缺口**不报错、结果看起来也正常**：用户以为切的是 3:00 那段，
实际切的是片头。现在先判 `null`/空串再转数字。

## 顺带修的一处测试假绿

`test-ipc-channels` 的 `referenced()` 一直没剥注释就扫通道名 ——
新工具注释里写了 `"mm:ss.xxx" / "mm:ss"` 这种时间格式示例，
被正则当成一个通道名 `mm:ss`，报「渲染层在用但主进程没注册」。

`registered()` 早就剥了注释（它的注释里解释了为什么必须剥），
`referenced()` 一直漏着，只是之前侥幸没撞上。现在两边一致。
这不是加一条白名单能根治的问题：注释里写任何形如 `a:b` 的示例都会误报，
而本项目到处在注释里写示例。

## 验证

**新增 `scripts/test-video-trim.js`（11 条，真跑 ffmpeg）**。
视频裁剪的正确性几乎全在「命令行怎么拼」上，而拼错了 ffmpeg 常常**照样返回成功**。
所以这组测试起真 ffmpeg、造真视频、切完用 ffprobe 量时长、用 PSNR 比对首帧：

- 参数校验：负起点 / 0 时长 / null / 非数字 一律拒绝
- 输出路径等于输入 → 拒绝，且源文件仍在
- 精确模式：3.0s 起切 2 秒 → 时长 2.0±0.1，首帧 PSNR 更接近源的 3.0s 帧而非 2.0s 帧
- 快速模式：**必须有偏差**（若哪天变精确了，说明 ffmpeg 行为变了，需重新评估文案）
- 进度：多条、递增、落差 > 5 个百分点、有 done
- 取消：进程被杀留下的残片必须被清掉，且下一次执行能正常完成
- 边界：整段裁剪、请求时长超过源剩余部分

**变异测试**（每条都验证过"改坏会红"）：
- 删 `-progress pipe:1` → 进度 0 条，红
- 删取消分支的 `fsp.rm` → 取消后仍留残片，红
- 把 `-ss` 挪到 `-i` 后 → **不红**（与实测结论一致：重编码时两者等价，属正确行为）

过程记录：进度断言最初写「至少 1 条 pct 且最大值 > 0」，删掉 `-progress`
之后它照样通过（`done` 事件是 handler 自己发的）。改成「多条且递增」后
又发现 320×240 的源编 10 秒只要 0.4 秒、凑不出多条 —— 于是给这条用
例单独造一份 720p 源。**一个防护被另一个更宽的条件遮住，是这类断言最常见的假死法。**
