# v0.9.4 —— 取消/生命周期收口 + 测试环境根治

本版做了两件事：修掉一批"界面说成功、实际没生效"的缺陷，以及把长期被判为
「环境限制」的 19 个 E2E 失败彻底根治（那是两个可修复的环境障碍，不是产品问题）。

## 一、P0 定时关机/重启「假成功」

**根因在 `runCmd`**：原判定是 `if (err && !stdout) reject; else resolve({code})` ——
**只要进程打印过任何内容**，非零退出就会被当成成功返回。于是
`shutdown /s /t 1800` 被系统拒绝（1116 权限 / 1190 已有计划）时，界面照样
启动倒计时并承诺"系统将在 N 分钟后关机"，实际什么都没排上。

- `runCmd` 改为按**退出码**判定：非零默认 reject（错误对象带 `stdout`/`stderr`/`code`）。
- 保留 `allowNonZero: true` 逃生门，给 7 个**确实依赖**"非零也拿结果"的查询类调用
  逐条标注理由：`reg query`×3、`where es`、`netsh wlan show profiles`、`sc.exe`、`powercfg /list`。
  写操作（`reg add`/`reg delete`）不加 —— 它们失败必须抛。
- `arm` 检查退出码：非零不 arm、不写成功文案，报错带退出码与首行 stderr。

## 二、P0 取消定时「可能没取消却报已取消」

`cancel()` 原来把 `mode`/`targetTs` 先清零，再用 `try/catch` 吞掉 `shutdown /a`
与**每个** `ONCE_REMOVE` 的错误，最后无条件写"已取消定时任务"。
取消失败时系统里的关机计划仍在，而界面说已取消 —— 比"没取消"更危险。

重写为「先收集真实结果」：逐项执行、各自记账（原来一个 catch 包住整个循环，
第一条失败后剩下的全不执行）；**全部成功才清状态**；有失败则保留可操作状态，
状态行红色「取消失败，计划可能仍在生效」，并提示可手动 `shutdown /a`。

## 三、P1 停止/取消在 invoke 返回前基本无效

7 个长任务页面（内容搜索、Ping、路由追踪、下载、视频压制、裁剪、格式转换、环境安装）
都曾有一个窗口期：点了开始、`invoke` 还没返回时 `jobId` 仍是 `null`，
此时点停止什么也不做；等 `invoke` 返回后 token 未变，任务照样启动。

统一改为 **per-run 序号**：第一个 await 之前领序号；停止/取消先 `runSeq++`，
再 kill 已知 id，并**立刻复位按钮/状态行/进度**；每个 await 返回点判 token，
过期分支 kill 自己拿到的 id、清 jobId、退订、隐藏进度，**不碰界面**。

新增 `lib/run-token.js` 承载判定逻辑（纯函数、可单测）。

## 四、P1 媒体长任务离开页面后继续跑

视频压制 / 裁剪 / 格式转换的 cleanup 原来只退订不 kill，图片压缩连 cleanup 都没注册。
切页后 ffmpeg 继续写盘，而页面既没有进度也没有取消入口 —— 「既续跑又让界面冻结」
是最差的组合。现在四个页面都在 cleanup 里 kill 当前任务、退订、复位，
并在 `onEnter` 恢复一致状态；图片压缩的循环同时检查 `cancelFlag` 与 token，
**离开后不再写新文件**。

## 五、P1 下载过期分支泄漏订阅

`start()` 在 `GET_INFO` 之后、`invoke` 返回后各有一次 token 判定。原实现 stale 分支
只 kill 就 return，而 `finally` 的条件是 `!jobId` —— 若首条 `job:stream` 抢先认领了
jobId，finally 就不做任何清理，监听器/进度/按钮全部残留，界面永远停在"下载中"。
现在 stale 分支自己做完整收尾，`finally` 条件改为 `stale || !jobId`。

## 六、P2 媒体页 onCleanup 在 await 之后注册

三个媒体页原来在 `await FFMPEG.STATUS` **之后**才 `App.onCleanup(unsub)`。
用户在这段预检期间切页时，旧页面没有任何清理，稍后的注册会被塞进**新页面**的
全局队列（旧订阅没人退、新页面离开时替旧页面退订）。
改为在 render 时注册稳定的页面级 cleanup，异步回调里只更新 `pageUnsub` 的值。

## 七、P2 系统定时 `onEnter` 的「已触发」分支不清状态

过期分支只写"已触发"就 return，`mode` 仍非空，随后 cleanup 把它覆盖成
「<mode>（已交给系统）」，与"已经到点执行完了"的事实矛盾。
现在同时清 `mode`/`targetTs`，文案改「已触发（已结束）」。

## 八、P2 局域网扫描离开后状态行/按钮未复位

`LAN.SCAN` 是阻塞式、没有 job id，cleanup 只能隐藏进度条。用户返回时会看到
「正在扫描…」+ 灰色按钮 + 没有进度条 —— 像卡死。现在 cleanup 与 onEnter
都复位按钮与状态行，并说明"上一轮结果作废、后台会自行收尾"。

## 九、测试环境根治（本轮最大收益）

19 个 E2E 长期失败、被判为「无桌面会话」—— 实测**该结论是错的**
（`SessionId=1`、`UserInteractive=True`）。真实原因是两个可修复的障碍：

1. **Chromium 进程级沙箱起不来**：`electron.exe --version` 直接以
   `0x80000003` 崩溃，stdout/stderr 全空；加 `--no-sandbox` 后正常。
   产品 `webPreferences` 的 `sandbox: false` 是**渲染进程**开关，管不到它。
2. **安全软件拦 Chromium 子进程写 `%TEMP%`**（`EPERM`）：探针都要把结果落盘再读，
   于是全部卡在"写不了结果文件"。

新增 `scripts/lib/electron-launch.js` 集中记录根因与必需参数，并在三处入口接入
（`run-tests.js`、`harness.js`、30 个不用 harness 的脚本），把测试树的
`TEMP`/`TMP` 与 `--user-data-dir` 统一重定向到工作区内的 `.tmp-testrun-*`（退出即删）。

**效果**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 失败脚本 | 19 | **0** |
| 通过断言 | 2013 | **2341** |
| 环境跳过 | 14 | **7**（全部是真实环境限制） |
