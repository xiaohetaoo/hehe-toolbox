# v0.8.4 —— 六项缺陷修复：电源门禁绕过、非递归删除系统文件、拖拽串页

这一版**没有新功能**。v0.8.3 发布后做了一轮独立代码审查（报告见 `reports/code-review-2026-11-12.md`），查出六个缺陷，本版全部修掉。

其中两个在安全/数据完整性方向，建议所有用户升级。

---

## 一、电源门禁可被 `if` / 花括号块 / `iex` 绕过（安全 · 高）

**问题的严重性**：应用里有一个「系统电源操作」开关，默认关闭，目的是防止未开启该能力的用户通过「命令收藏 / 快捷启动 / 定时任务」关掉机器。这个门禁原先只认「段首首词」，于是下面这些写法**全部放行**，而它们在 cmd / PowerShell 里是真的会关机：

```
if 1==1 shutdown /s
if exist C:\Windows shutdown /s /t 0
cmd /c if 1==1 shutdown /s
powershell -c "if ($true) { Stop-Computer }"
powershell -c "& { Stop-Computer }"
powershell -c "Invoke-Expression Stop-Computer"
powershell -c "iex 'Stop-Computer'"
powershell -c "foreach ($i in 1..1) { Stop-Computer }"
powershell -c "while ($true) { Stop-Computer }"
```

**修法**（与项目里既有的 `for` 循环体处理保持同一套思路）：

- 新增 `extractBraces()`，把 PowerShell 的 `{ … }` 语句块当作独立可执行位再判一次 —— 配平扫描、跳过引号内字面量、支持嵌套；
- 新增 `stripIfCondition()`，剥掉 `if [not] <条件>` 前缀后再看首词。条件形态太多（`1==1` / `exist X` / `not exist X` / `%v%==0` / `($true)`），逐种枚举必漏，所以判据是「跳过条件关键字与比较式」；
- `iex` / `Invoke-Expression` 按「字符串即代码」**fail-closed** —— 同一取舍也用在 `-EncodedCommand`：内容编成字符串就不可静态判定，此时按「可能是电源操作」处理。

**同时保住了放行面**：`if 1==1 shutdown /a`（在 if 里取消关机）仍正确放行；`if 1==1 echo hi`、`powershell -c "if ($true) { Write-Output hi }"` 等日常命令不误拦。门禁一旦开始误报，用户就会把高危开关常开，门禁等于失效 —— 所以「必须拦」和「必须放行」两侧都写了断言。

## 二、非递归删除放行系统目录深层文件（数据安全 · 高）

`checkDeletable` 的深层保护被 `if (recursive && …)` 限定，只在**递归**删除时生效。于是非递归删单个文件时：

| 路径 | 修复前 | 修复后 |
|---|---|---|
| `C:\Windows\System32\config\SAM` | 放行 | 拦截 |
| `C:\Windows\System32\drivers\etc\hosts` | 放行 | 拦截 |
| `C:\Program Files\app\x.dll` | 放行 | 拦截 |

目录因 `rm(recursive:false)` 遇非空会报 ENOTEMPTY 天然受限，但 `hosts`、`SAM` 这类**文件**在管理员 + 已开「文件删除」时能被真删 —— 删掉 hosts 就是全机 DNS 失效。

而 `ipc/fs-ops.js` 的注释本来就承诺「非递归删除单个文件时，仍然要挡住关键目录里的文件」，实现与意图相悖。

**不误伤验证**：`isCriticalDeep` 只覆盖 Windows / Program Files / ProgramData，**不含 Users**。实测 10 条路径：用户桌面 / 下载 / 文档 / 其他盘（含递归）全部照常可删，系统目录一律拦。提示语也按递归与否分开，非递归时不说「递归删除」。

## 三、全局拖拽可能拿错文件（潜在串页 · 低）

`takePending(toolId)` 的注释写着「只有发起方是它时才返回，避免串页」，但函数体**从未引用 toolId** —— 任何工具调用都会取走全局队列。

真实可复现：拖文件给工具 A，A 的 picker 还没消费（消费挂在 `setTimeout(0)` 上），用户先切到工具 B，B 就把本该属于 A 的文件取走了。「取完即清空 + 30 秒过期」挡不住这种情况 —— 那两条只解决陈旧队列，解决不了「另一个工具先到」。

修复后入队时写入 toolId、取用侧比对；**不匹配只返回 null、不清空队列**，用户切回 A 仍能拿到。剪贴板面板那条同构修好。面板送图片的路径不带 toolId（那是「谁先看到谁用」），保持原行为。

## 四、两处背景透明（视觉 · 中）

`disk-health` 的结论框与 `mojibake-fix` 的结果框引用 `var(--fill-1)`，而**全项目没有这个定义**且无回退。浏览器对未定义变量静默回退，整条 `background` 在计算期失效 → 两处背景透明、与周边卡片不一致，**控制台一个字都不报**。与 v0.8.3 修的 `--bg-1` 是同一类问题，改用 `--bg-2`。

**同时补上了测试盲区**：`test-css-vars.js` 原来只扫 `css/app.css` 与三个辅助窗口，不扫 `js/` 里的内联样式，所以写在工具页里的 `var()` 引用完全测不到。现在扩到 `js/**`。

## 五、拖拽触顶提示显示「0 个文件的上限」（UX · 中）

拖超大文件夹触顶时，全局拖拽那条路径把上限硬编码成 0，用户看到：

> 已达到 **0** 个文件的上限，剩余文件未加入

而工具页内拖拽传的是真实值 —— 同一功能两条路径，一条文案对、一条显示 0，且「去设置调大上限」的指引对着 0 无从下手。

根因是「上限由调用方提供」这个设计容易漏，所以修在 `expandNotice`：非正数时自己读 `Prefs`，两个调用点都不必关心。

## 六、`checkOverwritable` 缺类型闸门（健壮性 · 低）

兄弟函数 `checkDeletable` 因真实事故（`{path,depth}` 对象被降级成 `[object Object]` 导致闸门形同虚设）早已严格拒绝非字符串，但 `checkOverwritable` 仍是 `String(p || '')` —— `{}` 和 `123` 都返回「放行」。

下游 `writeFile` 对非字符串本身会抛错，所以不直接可利用；但闸门对垃圾输入说「放行」是纵深防御缺口。两处的类型校验抽成共用的 `stringPathOrError` 助手，一处维护。

## 修复之外的额外处理

- `scripts/test-path-guard.js` 里有 **89 行 `\r\r\n`（双 CR）** 的行尾污染，导致 `git diff` 显示 433 行假变化。已归一化，真实改动才看得清。
- 审查报告 F1 里有一条 `if %errorlevel%==0 echo ok` 会被拦。用修复前的版本对照实测确认：**修复前就是如此**，属 `hasUnknownVar` 的 fail-closed（变量内容不可静态判定）。这是刻意的保守取舍 —— 放宽它等于给 `%FOO% shutdown /s` 留一条绕过路径。所以改的是测试用例，不是实现。

## 已知限制（未变）

- PDF 水印不支持中文（pdf-lib 标准字体只有 Latin-1，硬做会抛 `WinAnsi cannot encode "机"`）；
- 三栏对比不做自动合并（合并错了比不合并更糟）；
- 电源门禁是**语法层**防护，不是安全沙箱：能静态识别的形态都拦，但 `iex` 之类「字符串即代码」只能 fail-closed 整条拦。真正的边界仍然是「用户是否开启了这个能力」；
- 敏感内容清理基于形态判定，不能替代密码管理器。
